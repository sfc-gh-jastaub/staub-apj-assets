Every exception you have raised so far generates correspondence, and correspondence arrives faster than anyone can triage it. Some of it is a supplier confirming a corrected invoice; some of it is a business unit disputing a finding three days before lodgement. Both look identical in an inbox.

CORRESPONDENCE_TEXT on RAW_DATA.DOC_TAX_INVOICE holds the message attached to each document. This step reads the tone of it, so the queue can be worked in the order Brindabella's tax team should actually work it.

  • Return a sentiment label from free text with one function call.
  • Handle all four labels the function can return.
  • Turn the label into a triage priority their tax team can sort on.
⚠️
AI_SENTIMENT returns mixed as well as positive, negative and neutral

A CASE that handles only positive, negative and neutral does not fail, does not warn and does not return NULL — it silently drops every mixed row into whatever your ELSE branch says, and mixed is exactly the label you get on the messages that matter most: a supplier who is co-operative about the invoice and furious about the assessment. Write all four branches explicitly, every time. And never compare the output numerically: it is a label, not a score, so > 0.5 is meaningless here.

Read the tone, next to the text

sql
WITH correspondence AS (
    -- Bound the population before the model sees it, as in every other step.
    SELECT DOC_ID,
           SOURCE_SYSTEM,
           SOURCE_DOC_REF,
           SUPPLIER_ID,
           BOOKED_SUPPLY_CATEGORY,
           CORRESPONDENCE_TEXT
    FROM RAW_DATA.DOC_TAX_INVOICE
    WHERE CORRESPONDENCE_TEXT IS NOT NULL
    LIMIT 25
)
SELECT
    DOC_ID,
    CORRESPONDENCE_TEXT,
    AI_SENTIMENT(CORRESPONDENCE_TEXT):categories[0]:sentiment::VARCHAR AS SENTIMENT_LABEL,
    -- All four labels. Not three.
    CASE AI_SENTIMENT(CORRESPONDENCE_TEXT):categories[0]:sentiment::VARCHAR
         WHEN 'negative' THEN '1 - URGENT'
         WHEN 'mixed'    THEN '2 - REVIEW'
         WHEN 'neutral'  THEN '3 - ROUTINE'
         WHEN 'positive' THEN '4 - MONITOR'
         ELSE                 '9 - UNCLASSIFIED'
    END AS TRIAGE_PRIORITY
FROM correspondence
ORDER BY TRIAGE_PRIORITY, DOC_ID;

Read the second and third columns together for a minute. The negative messages are the ones disputing a finding or escalating a delay, and they are the ones with a deadline attached. The mixed rows are the interesting ones: a message that thanks the team for the correction and then objects to the amount is genuinely both, and forcing it into positive or negative would lose the half that needs a response.

LabelTriage priorityWhat it usually means in practice
negative1 - URGENTA dispute, an escalation or a complaint. Someone is waiting and unhappy about it.
mixed2 - REVIEWCo-operative on one point and objecting on another. Needs a human to read it properly.
neutral3 - ROUTINEA factual note. Acknowledge and file.
positive4 - MONITORA confirmation that something has been resolved. No action beyond closing the item.

Persist it, and see the shape of the queue

sql
CREATE OR REPLACE VIEW AI_INSIGHTS.V_AI_CORRESPONDENCE_TRIAGE AS
WITH correspondence AS (
    SELECT DOC_ID,
           SOURCE_SYSTEM,
           SOURCE_DOC_REF,
           SUPPLIER_ID,
           BOOKED_SUPPLY_CATEGORY,
           CORRESPONDENCE_TEXT
    FROM RAW_DATA.DOC_TAX_INVOICE
    WHERE CORRESPONDENCE_TEXT IS NOT NULL
    LIMIT 25
),
scored AS (
    SELECT c.*,
           AI_SENTIMENT(c.CORRESPONDENCE_TEXT):categories[0]:sentiment::VARCHAR AS SENTIMENT_LABEL
    FROM correspondence c
)
SELECT
    s.DOC_ID,
    s.SOURCE_SYSTEM,
    s.SOURCE_DOC_REF,
    s.SUPPLIER_ID,
    s.BOOKED_SUPPLY_CATEGORY,
    s.CORRESPONDENCE_TEXT,
    s.SENTIMENT_LABEL,
    CASE s.SENTIMENT_LABEL
         WHEN 'negative' THEN '1 - URGENT'
         WHEN 'mixed'    THEN '2 - REVIEW'
         WHEN 'neutral'  THEN '3 - ROUTINE'
         WHEN 'positive' THEN '4 - MONITOR'
         ELSE                 '9 - UNCLASSIFIED'
    END AS TRIAGE_PRIORITY,
    (s.SENTIMENT_LABEL IN ('negative', 'mixed')) AS NEEDS_RESPONSE
FROM scored s;

-- The queue by priority. If '9 - UNCLASSIFIED' returns any rows, the CASE is
-- missing a label the function actually emitted - go and look at it.
SELECT TRIAGE_PRIORITY,
       SENTIMENT_LABEL,
       COUNT(*)                                  AS MESSAGE_COUNT,
       COUNT(DISTINCT SUPPLIER_ID)               AS SUPPLIERS,
       SUM(IFF(NEEDS_RESPONSE, 1, 0))            AS AWAITING_RESPONSE
FROM AI_INSIGHTS.V_AI_CORRESPONDENCE_TRIAGE
GROUP BY 1, 2
ORDER BY 1;

The '9 - UNCLASSIFIED' branch is a canary. All four documented labels are handled above it, so any row landing there means the function returned something the view does not know about, and you see it as a count rather than as a silently mis-prioritised message months later.

🔑
Sentiment is a routing signal, not a tax position

Nothing in this step changes a treatment, a rate or a return. An angry supplier is not evidence that the GST is wrong, and a grateful one is not evidence that it is right — the determination rules from Lab 1 remain the only thing that decides the tax outcome. What this gives their tax team is order of work: 25 messages sorted so the disputed and the partly disputed reach a human first, and the acknowledgements wait. NEEDS_RESPONSE is the column the queue actually filters on.

✅
Three kinds of evidence, all queryable

The narrative told you what was bought, the remarks told you what the invoice claimed, and the correspondence tells you how hard someone is pushing back. All three join to the ledger on (SOURCE_SYSTEM, SOURCE_DOC_REF), which is what keeps them part of the tax record rather than a separate pile.
